# TONBANKCARD V2 Analytics, Privacy, and Success Metrics Baseline

Date: 2026-04-30

Issue: [#10](https://github.com/labtgbot/marketcap/issues/10)

This baseline defines how TONBANKCARD V2 measures product outcomes without
over-collecting data. It extends the product requirements in
`docs/v2-product-requirements.md` with event names, allowed properties, identity
rules, retention windows, sensitive-data exclusions, KPI definitions, and
dashboard requirements that later implementation tasks can reference.

## Measurement Principles

- Collect the smallest event payload that can answer a product, reliability,
  safety, or compliance question.
- Keep anonymous website analytics separate from authenticated Telegram sessions.
  Do not join them unless the user enters a trusted Telegram session and the
  backend creates an explicit server-side link.
- Trust Telegram identity only after server-validated Telegram `initData`.
  Browser-provided Telegram globals are context hints until the backend verifies
  the signed payload.
- Treat wallet addresses, AI prompts, alert rules, referral attribution, and
  admin audit logs as sensitive product data, not generic analytics fields.
- Prefer coarse categories, hashes, booleans, and route identifiers over raw
  user-entered values.
- Store aggregated KPI history longer than raw user-level events.
- Make analytics optional by deployment policy. Core market routes, legal pages,
  watchlists, and alerts must work when analytics collection is disabled.

## Identity Rules

| Context | Identifier | Allowed joins | Forbidden joins |
| --- | --- | --- | --- |
| Anonymous public website | Random `anonymous_session_id` stored in first-party browser storage after consent or legitimate-interest review. Rotate at least every 30 days. | Same-session page, search, share, local watchlist, and performance events. | Telegram user id, wallet address, IP address, AI prompt text, or admin actor data. |
| Authenticated Telegram sessions | Internal `user_id` created after server-validated Telegram `initData`; raw Telegram ids stay in the application database. Analytics receives `telegram_user_id_hash` only when user-level analysis is needed. | Watchlist, alert, referral, share, AI feedback, premium, and retention events for the same trusted user. | Anonymous website session history unless the backend explicitly links the current session after validation. |
| Telegram group context | Hashed `chat_instance` or internal `group_context_id` when group flows are enabled. | Group share, inline card, campaign, and group-context events. | Personal watchlist, personal alert rules, raw chat title, member list, or usernames. |
| Admin operator | Internal `admin_actor_id` for audit and security events. | Admin setting changes, provider changes, feature flag updates, and support access logs. | Public website analytics, Telegram personal events, or raw secret values. |
| Future wallet-aware features | Hash of normalized public wallet address and network only when the user enables a wallet feature. | Wallet-aware watchlist or read-only portfolio events needed for the selected feature. | Private keys, seed phrases, wallet signatures, raw address in client logs, or unrelated Telegram events. |

Identity implementation notes:

- `anonymous_session_id`, `event_id`, and `request_id` must be opaque UUID-like
  values with no embedded timestamp, IP, user id, or route data.
- Store raw Telegram ids only in the application database tables that need them
  for bot delivery, session validation, support, or deletion workflows.
- Use a stable server-side hash salt for analytics ids. Rotate the salt only
  with a documented migration plan because rotation breaks retention cohorts.
- Attribution must be first-touch for a campaign unless product leadership
  explicitly approves another model. Later referrals must not overwrite the
  original inviter on an existing trusted Telegram user.

## Event Taxonomy

Every event uses the common envelope below plus event-specific properties.

| Common field | Requirement |
| --- | --- |
| `event_name` | One of the approved names in this document. |
| `event_id` | Unique id generated by the client or server for deduplication. |
| `occurred_at` | ISO 8601 UTC timestamp from the server when available. |
| `surface` | `public_web`, `mobile_web`, `telegram_mini_app`, `telegram_bot`, or `admin`. |
| `route` | Normalized route pattern such as `/`, `/coins/:id`, or `/app/coin/:id`. |
| `identity_mode` | `anonymous`, `telegram_user`, `telegram_group`, `admin`, or `system`. |
| `session_id` | Opaque anonymous or trusted session id. |
| `request_id` | Backend request id when the event is server-generated or API-backed. |
| `feature_flags` | Optional list of enabled feature keys relevant to the event. |
| `app_version` | Release or commit identifier for debugging regressions. |

### Reliability and Admin Events

| Event | When | Required properties | Identity mode | Raw retention |
| --- | --- | --- | --- | --- |
| `web_vital_recorded` | Browser sends Core Web Vitals or first meaningful content timing. | `metric_name`, `metric_bucket`, `route`, `surface`, `connection_type` | anonymous or telegram_user | 30 days |
| `frontend_error_seen` | Client captures a safe frontend error. | `error_code`, `route`, `surface`, `component`, `release` | anonymous or telegram_user | 30 days |
| `api_request_completed` | Backend request completes for V2 API routes. | `endpoint`, `status_bucket`, `latency_bucket`, `cache_state`, `provider` | system | 30 days |
| `provider_health_changed` | Provider health transitions between healthy, degraded, or down. | `provider`, `old_state`, `new_state`, `reason_code` | system | 180 days |
| `admin_setting_changed` | Admin changes feature flags, provider settings, legal copy status, curated TON assets, or alert limits. | `setting_group`, `action`, `admin_actor_id`, `audit_id`, `approval_state` | admin | 365 days |
| `admin_support_viewed` | Support operator opens a user or alert diagnostics view. | `admin_actor_id`, `view_type`, `subject_id_hash`, `reason_code` | admin | 365 days |

Event property rules:

- Use `coin_id`, `symbol`, `route`, `source_route`, `surface`, and coarse
  buckets instead of raw search text, raw prompt text, exact wallet address, IP
  address, or user agent strings.
- `query_length_bucket` may be `empty`, `1-2`, `3-5`, `6-10`, or `11-plus`.
  Raw search queries are not analytics properties.
- `threshold_bucket` may describe alert magnitude, for example `lt_1_percent`,
  `1_5_percent`, `5_10_percent`, or `gt_10_percent`. Store exact alert rules in
  application tables only.
- `latency_bucket` and `metric_bucket` should use fixed ranges so dashboards do
  not need raw timing for most views.
- `amount_bucket` may group premium purchase amount; the analytics stream does
  not receive payment account identifiers.

## Retention Windows

| Data class | Retention | Notes |
| --- | --- | --- |
| Anonymous raw analytics events | 90 days | Enough for funnel debugging and short-term cohort comparison. Rotate browser ids at least every 30 days. |
| Trusted Telegram raw product events | 180 days | Supports D7 and D30 retention, alert usefulness, referrals, and support diagnostics. Subject to deletion workflows. |
| Alert delivery records | 180 days after delivery or 90 days after alert deletion, whichever is earlier unless needed for abuse review. | Store `alert_id_hash`, status, and buckets in analytics; exact rules stay in application tables. |
| Achievement and streak events | 180 days | Supports opt-in retention analysis. Achievement prompts must remain dismissible and should not contain raw user content. |
| Premium entitlement audit events | 365 days or the minimum business/accounting period selected before launch. | Payment provider identifiers and receipts stay in payment records, not analytics events. |
| Admin audit logs | 365 days minimum. | Required for security review, support accountability, provider changes, and feature flag changes. |
| Operational request, performance, and frontend error logs | 30 days raw, 13 months aggregate. | Raw logs should be sampled where volume is high and should exclude sensitive fields. |
| AI prompt diagnostics | Disabled by default; if enabled for an incident, retain redacted records for at most 7 days. | Product analytics stores prompt version and safety state, not prompt text. |
| Wallet-aware diagnostics | 30 days raw hash-only diagnostics when the feature exists. | No raw wallet addresses in analytics or client logs. |
| Aggregated KPI tables | 25 months. | Aggregates must remove user-level ids and support monthly launch comparisons. |
| Consent and deletion records | As required to honor legal and compliance obligations. | Store the request trail without retaining deleted event payloads. |

## Sensitive Data Classification

| Data type | Classification | Allowed storage | Client logging rule |
| --- | --- | --- | --- |
| Public market data, coin ids, exchange ids, route names | Public or low sensitivity | Client cache, server cache, analytics events. | Allowed when not combined with sensitive identity. |
| Anonymous session ids and event ids | Pseudonymous analytics data | First-party storage and analytics stream. | Allowed only as opaque values; rotate and clear on consent withdrawal where applicable. |
| Telegram user data | Restricted personal data | Application database after validated Telegram session; hashed id in analytics only when needed. | Raw Telegram id, username, phone, photo URL, raw `initData`, and chat metadata are excluded from client logs. |
| Wallet addresses | Sensitive pseudonymous data | Application database only for enabled wallet-aware features; analytics may use salted hash and network. | Raw wallet addresses are excluded from client logs and analytics events. |
| AI prompts and AI responses | Restricted content data | Redacted, short-lived diagnostic store only when explicitly enabled; cache summaries by prompt version and market data ids. | Raw AI prompts, user-entered prompt text, and complete model responses are excluded from client logs. |
| Alert rules | Sensitive product preference | Application database for active alerts; analytics uses trigger type and threshold buckets. | Exact thresholds and quiet-hour details are excluded from client logs unless needed in the user's own UI state. |
| Referral payloads | Pseudonymous attribution data | Application database and analytics with campaign and hashed inviter. | Raw inviter id and unvalidated payload contents are excluded from client logs. |
| Premium payment data | Restricted payment data | Payment provider and entitlement tables. | Receipts, payment account ids, and invoice payload secrets are excluded from client logs. |
| Admin audit logs | Restricted operational data | Server-side audit tables with role-based access. | Audit diffs are not exposed to public clients; secret previous and next values are never logged. |
| Secrets and provider keys | Prohibited in analytics | Secret manager, environment, or server config only. | API keys, bot tokens, database passwords, Upstash tokens, Groq keys, and ChangeNOW private values are excluded from client logs. |

The following fields are explicitly excluded from client logs, analytics events,
and browser-visible error payloads: raw Telegram `initData`, bot tokens, API
keys, database credentials, raw Telegram ids, usernames, phone numbers, raw
wallet addresses, private keys, seed phrases, raw AI prompts, full AI responses,
payment receipts, exact alert rules, and admin secret values.

Privacy implementation notes:

- Client-side logging must use an allowlist. New fields are dropped by default
  until the analytics schema accepts them.
- Backend logs must redact request bodies for Telegram session validation,
  alerts, AI, payments, admin settings, and wallet-aware endpoints.
- Support tooling may show the minimum data needed to resolve a user request,
  and every support view must emit `admin_support_viewed`.
- User deletion must remove or anonymize trusted Telegram analytics joins while
  preserving aggregate KPI history.
- Privacy and cookies copy must be updated before enabling third-party
  analytics cookies, cross-site pixels, AI prompt diagnostics, wallet-aware
  features, or premium payments in production.

## KPI Definitions

| KPI area | Definition | MVP acceptance | Launch target direction |
| --- | --- | --- | --- |
| Activation | A session reaches first meaningful market content and performs at least one discovery action: search result select, coin detail view, TON view, watchlist add, alert create, share start, achievement opt-in, or swap widget open. | Dashboard can report activation rate by `surface`, `source_route`, and data state. | Improve first-session discovery without increasing frontend error rate. |
| Retention | Trusted Telegram user returns to the Mini App or bot after first activation. Track D1, D7, D30, and achievement streak cohorts. Anonymous website retention may be reported only as rotated-session return. | D7 Telegram retention and achievement streak counts can be calculated from trusted sessions and product events. | Improve D7 return after watchlist, alert delivery, and achievement launch. |
| Virality | Share or referral loop creates a recipient open: `share_started` or `share_completed` followed by `share_opened`, `referral_opened`, or `referral_attributed`. | Dashboard shows shares, opens, attribution rate, and campaign breakdown. | Increase useful share opens while monitoring spam, mute, and unsubscribe signals. |
| Alert usefulness | Delivered alerts lead to an open, watchlist action, alert edit, or positive feedback without high mute, pause, delete, or unsubscribe rates. | Dashboard shows delivery success, open rate, useful feedback, noisy feedback, and opt-out rates. | Improve useful alert rate while reducing noisy and late feedback. |
| Performance | Public web and Telegram Mini App routes meet route-specific first meaningful content, API latency, bot delivery, and error-rate budgets. | Dashboard shows p50, p75, p95 timing buckets for core routes and API endpoints. | Keep mobile market pulse fast under provider degradation and Telegram bursts. |
| TON engagement | User opens TON ecosystem views, Toncoin detail, TON-tag filters, or TON share cards. | `ton_viewed` is available by route and source. | Establish TON as a differentiated discovery path versus generic market browsing. |
| AI usefulness and safety | AI insights are viewed, rated helpful, and rarely marked stale, wrong, unsafe, or advice-like. | AI dashboard works while AI can remain disabled by feature flag. | Improve useful ratings and keep unsafe feedback near zero before launch expansion. |
| Revenue readiness | Premium exposure reaches checkout starts and confirmed entitlement without payment errors. | Premium funnel can be measured behind feature flags without exposing payment details. | Validate Telegram Stars packaging before broad launch. |
| Operational reliability | Provider health, cache state, API errors, bot failures, and admin changes are visible to operators. | Operators can detect degraded provider, cache, API, and bot states from dashboards. | Reduce time to diagnose provider and delivery incidents. |

## Dashboard Requirements

Dashboards must use aggregate views by default. User-level drilldown is allowed
only in role-restricted support or security tools and must create audit events.

| Dashboard | Required views | Required filters |
| --- | --- | --- |
| Product funnel | Market pulse viewed, search opened, result selected, coin detail viewed, TON viewed, watchlist added, alert created, achievement unlocked, share started, swap widget opened, AI insight viewed, premium conversion completed. | Date, surface, route, source route, data state, feature flags, anonymous vs Telegram. |
| Retention cohorts | Telegram D1, D7, D30 returns; anonymous rotated-session returns; first action cohort; achievement streak cohort. | Cohort date, surface, first action, campaign, alert-enabled users, achievement id. |
| Virality and referrals | Share starts, share opens, referral opens, referral attribution, campaign conversion, invite loop rate. | Campaign, share channel, payload type, landing route, Telegram vs public web. |
| Alert usefulness | Alert creates, deliveries, failures, opens, edits, pauses, deletes, feedback, unsubscribe or mute events. | Trigger type, coin id, delivery channel, latency bucket, quiet-hours enabled. |
| Search and TON discovery | Search opens, result rank selection, zero-result rate, TON views, TON category engagement. | Surface, route, query length bucket, result type, TON category. |
| AI safety and usefulness | AI views, provider/model, prompt version, cache/freshness, feedback, unsafe/wrong/stale rates. | Insight type, provider, model, prompt version, safety state, feature flag. |
| Performance and reliability | Web vitals, API latency, provider health, cache state, frontend errors, bot delivery latency. | Route, endpoint, provider, surface, release, profile. |
| Admin and privacy operations | Admin setting changes, support views, deletion requests, consent state changes, schema validation failures. | Actor role, setting group, action, reason code, date. |

Dashboard operating requirements:

- Show data freshness, event volume, schema rejection count, and sampling rate on
  every operational dashboard.
- Store dashboard definitions or documented queries in the repository before
  public launch.
- Keep UTC as the canonical reporting timezone. Product dashboards may add
  local display only as a presentation option.
- Do not expose raw Telegram ids, wallet addresses, AI prompts, payment data, or
  exact alert rules in dashboards.
- Exported CSV or BI views must contain aggregates unless an admin role has a
  documented support or security reason for row-level access.
- Add a privacy review checkpoint before enabling third-party analytics tools,
  persistent cookies, or cross-site campaign pixels.

## Implementation Contract

Future implementation tasks should reference this contract when adding analytics
emitters, API endpoints, database tables, queues, or dashboards.

- Event emitters must call a single allowlisted analytics helper instead of
  sending arbitrary objects from route components.
- The helper must validate `event_name`, common fields, allowed property keys,
  value types, and maximum string lengths before sending data.
- Unknown fields must be dropped and counted as schema validation failures.
- Server-generated events should be preferred for trusted Telegram sessions,
  alert delivery, premium conversion, admin audit logs, and provider health.
- Browser-generated events are acceptable for public page views, search UI,
  share starts, swap widget opens, AI insight visibility, and web vitals after
  applying the client allowlist.
- All API errors returned to clients must include safe `error_code` and
  `request_id` values, not raw exception messages or provider payloads.
- Analytics implementation must be feature-flag friendly so deployments can
  disable collection without breaking user workflows.
- Schema changes require updating this document, the validation tests, and any
  dashboard definitions in the same PR.
