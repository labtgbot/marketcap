# TONBANKCARD V2 Performance, Load, And Reliability Hardening

Date: 2026-05-02

Issue: [#39](https://github.com/labtgbot/marketcap/issues/39)

## Objective

Keep the public website and Telegram Mini App responsive during normal traffic,
Telegram bursts, and upstream provider outages. The hardening contract uses
checked-in budgets, synthetic CI load checks, static asset cache headers, and
existing stale-data fallbacks instead of relying on manual launch review only.

## Performance Budgets

The canonical budget values live in `config/performance.php`.

| Budget key | Default | Measurement |
| --- | ---: | --- |
| `first_contentful_render_ms` | 1800 ms | Release checklist browser pass on public web and Telegram webview widths. |
| `app_ready_ms` | 2500 ms | Release checklist browser pass from navigation start until the Vue shell is interactive. |
| `market_api_p95_ms` | 350 ms | CI synthetic load for market pulse global stats and market rows. |
| `search_api_p95_ms` | 200 ms | CI synthetic load for first-party smart search suggestions. |
| `coin_detail_api_p95_ms` | 450 ms | CI synthetic load for coin detail provider envelope handling. |
| `chart_render_ms` | 900 ms | Browser smoke coverage plus release checklist chart interaction timing. |
| `alert_delivery_p95_ms` | 1000 ms | CI synthetic load for alert rule evaluation and delivery payload creation. |
| `share_card_generation_p95_ms` | 250 ms | CI synthetic load for Telegram `startapp` share-card payload generation. |

The CI harness writes `test-logs/performance-load-summary.json` with p50, p95,
max, iteration count, and pass/fail for each measured profile.

## Load Profiles

`tests/performance-load-check.php` keeps providers and storage in memory so CI
can measure route logic deterministically. Staging release drills should run the
same profile names against real Redis, MySQL, and provider credentials before a
public launch. The safe traffic assumptions below are starting points for that
drill, not guaranteed production capacity.

| Profile | Covered path | Safe traffic assumptions | Primary bottlenecks |
| --- | --- | --- | --- |
| `market_pulse` | `/api/market/global` and `/api/market/coins/markets` | 20 requests per second with Redis cache and coalescing enabled. | CoinGecko quota, Redis latency, serialized market row size. |
| `smart_search` | `/api/search?q=ton&limit=8` | 30 requests per second after the search index is warm. | Search index rebuild cadence and Redis availability. |
| `coin_detail` | `/api/market/coins/bitcoin` | 15 requests per second for hot assets with stale fallback enabled. | Provider latency, large coin metadata payloads, chart tab follow-up requests. |
| `alert_evaluation` | `/api/alerts/evaluate` helper path | 1200 rules per minute per worker shard before adding more workers. | MySQL due-rule selection, market row fan-out, Telegram delivery retries. |
| `share_card_generation` | `/api/share/resolve` payload helpers | 40 share payload operations per second per PHP worker. | Payload validation, attribution writes when trusted Telegram sessions are present. |

## Cache And Provider Outage Mode

The market gateway continues to use the cache, stale fallback, and request
coalescing rules in `docs/v2-cache-rate-limit-coalescing.md`. During a provider
outage, cached market responses return `meta.freshness.cache_status=stale`,
`upstream_fallback=true`, and `stale_age_seconds` so the UI can keep rendering
with visible freshness warnings.

If no cached market data exists, the market pulse route shows an explanatory
provider-unavailable alert instead of a blank screen. Coin charts lazy-load
ECharts only when needed and show the existing chart-specific fallback when
chart data or the chart runtime is unavailable.

## Static Asset Cache Policy

Application asset URLs generated by `get_file_url_for_display()` include a file
timestamp query parameter. Versioned CSS, JavaScript, image, and font assets use:

```text
Cache-Control: public, max-age=31536000, immutable
```

Unversioned static assets use a shorter public cache with
`stale-while-revalidate`, while `service-worker.js` stays revalidatable with
`no-cache, no-store, must-revalidate` so PWA updates can activate quickly.
The local PHP router applies the same policy for reproducible tests; production
Nginx or Apache deployments should mirror these headers at the edge.

## Tests

Run the issue #39 regression check with:

```sh
npm run test:performance
```

The aggregate `npm test` command runs the performance check in CI and uploads
the `test-logs/` artifact. The check verifies budget configuration,
static-header behavior, provider outage documentation, chart lazy loading,
load profiles, and p95 timing for market pulse, smart search, coin detail,
alert evaluation, and share-card generation.
